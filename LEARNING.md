# Learning log

Devlog for FirstCommit. One entry per build phase.

## Phase 0 — Foundation (2026-09-25)

- **Scaffolded instead of guessing versions.** Ran `create-expo-app` into a temp directory and lifted the parts we needed, rather than hand-writing `package.json`. It pins a coherent set — Expo SDK 57, React 19.2.3, React Native 0.86.3, RN Web 0.21, TypeScript 6.0.3 — that we would have got subtly wrong by hand. Then deleted the template's example screens, components, hooks and demo assets instead of keeping them "for later".
- **Skipped npm workspaces.** `packages/core` and `packages/transport` are plain folders reached through tsconfig `paths`, which Metro resolves natively. No `watchFolders`, no hoisting surprises, one `npm install`. Worth revisiting only if a package ever needs to be published on its own.
- **The docs were wrong about layout, and the framework proved it.** We had specified `app/storage/` for the observation store, but `app/` is the Expo Router routes directory — every file in it becomes a route, so the store would have been served as a page. Routes moved to `src/app/`, non-route code to `src/`. A layout that reads fine on paper can be wrong the moment a real framework touches it.
- **Made core purity enforceable, then checked the enforcement.** `packages/core` must not import react/react-native/expo or touch the DOM. That is now an ESLint rule rather than a convention — and we verified it by adding a deliberate `import { Platform } from "react-native"`, confirming lint failed, and removing it. An unverified guard is not a guard.
- **Proved the alias end to end, not just in the typechecker.** The static web export renders `PROTO_VERSION` from `@pasabi/core` into `dist/index.html`. `tsc` passing only means the types resolve; the exported HTML means Metro resolved it too.

## Phase 1 — Observations + incident engine (2026-09-25)

- **Writing the vectors before the engine paid for itself immediately.** Eleven cases, expectations computed by hand from BR-003 to BR-010, committed before a line of `compute` existed. Eight of them failed on the first run for a reason no amount of re-reading the spec would have surfaced: `-Math.min(0, 20)` is **negative zero**, and `-0` is a distinct value that compares unequal to `0` and survives into JSON snapshots and sync payloads. Fixed with `0 - x` instead of `-x`. Had the vectors been generated from engine output, the bug would have been enshrined as correct.
- **The architecture asked for a spatial grid we did not need.** ARCHITECTURE prescribed a 150 m grid for O(n) grouping. A time-sorted window scan with a cheap latitude pre-reject computes 3,000 observations into 1,705 incidents in **6.9 ms**, roughly 40x inside the 300 ms budget. We benchmarked first and wrote the doc back, rather than implementing a grid on the strength of a guess about performance.
- **R-1 is not a detail, it changes the grouping graph.** Area text links a pair only when at least one of them lacks a GPS fix, which means the area-text pass cannot be a simple consecutive-pairs walk: a no-fix observation has to link to every bucket member inside the window, because two GPS-bearing neighbours it bridges may never link to each other directly. Getting that wrong would have silently split incidents.
- **BR-008 needed a real ordering, not a sentence.** "Evict the lowest-urgency incident but keep its earliest and latest" only means something once you compute incidents inside the store policy and rank them. The R-5 last-resort rung has its own test with the pathological case: a store holding nothing but this device's own un-uploaded observations. It now sheds the oldest rather than refusing to record a new emergency.
- **`tsc` caught what Vitest did not.** Vitest transpiles without typechecking, so the vector loader ran green while `npm run typecheck` failed on missing Node types. Four gates that disagree are worth more than one that passes.

## Phase 2a — Encounter sync over the mock transport (2026-09-25)

- **A "test harness bug" was really a protocol bug.** Two tests lost observations (28 of 60 arrived). The first fix was to drain the unawaited `receive()` promises in the harness, and everything went green. That was the wrong conclusion: tracing it properly showed that answering a peer BYE *mid-batch-loop* sent our own BYE and resolved `finished` while observations were still going out. In the field a carry service would have torn down a live connection. Fixed with a `sending` flag, and pinned with an assertion that checks `observationsSent` BEFORE the drain, so the real bug cannot come back hidden behind the harness fix.
- **R-9 is worth what it cost.** 16 raw bytes per ID makes a 3,000-ID summary 48 KB and two payloads at the 30 KB ceiling. As 36-character strings it is ~111 KB and four. The chunking maths in ARCHITECTURE section 4 only works because of the binary encoding, and there is now a test asserting exactly that arithmetic.
- **The mock transport is the reason Phase 2a exists at all.** Three simulated devices converge to identical incident lists, a MEDICAL observation travels A to C via a carrier that never meets C, and 100 observations cross in 151 ms over 7 payloads against a 10 s budget. None of it needed a phone. What it does NOT prove is that any radio works, and both the page and the test say so out loud.
- **Keeping core ignorant of Transport paid off immediately.** `SyncSession` takes a `send` callback rather than a `Transport`, so `packages/core` still imports nothing platform-shaped, and the same session code runs under the mock in CI, in a browser page, and later under Multipeer or Nearby without changing a line.
- **The /sim route makes convergence something the team can see.** It runs the real protocol in the browser on the Vercel preview, which is also the honest fallback for the demo video if hardware never materialises.

## Phase 3 — Station mode and the situation board (2026-09-26)

- **Building the board exposed a rule that punished the primary user.** BR-010 caps a device at six observations an hour, and acknowledgements are observations, so an operator working a busy board would be locked out after six taps. The limit exists to stop one device flooding the network with reports; applying it to operator actions aimed the anti-spam rule squarely at the person the product is for. Now counted for REPORT only, recorded as D-017, with a test that a station can still work the board after twenty acknowledgements.
- **Snapshot diffing matches on observation IDs, and that is not a detail.** An incident key is the smallest observation ID in the group, so evicting that single observation renames the incident while nothing about the situation changed. Keyed matching would have reported it as brand new. There is a test that evicts the key observation and asserts the incident is NOT flagged new.
- **No baseline means no highlights.** With no stored snapshot the diff returns empty rather than marking everything new. An operator opening the board to a wall of NEW badges learns nothing; the first "Mark as seen" is what starts the tracking, and the board says so.
- **The PIN is honest about what it is.** It gates a UI mode on a shared phone, hashed and salted with the per-install device ID rather than stored in the clear. It is not protecting the observations, which are already readable from My data, and a four-digit PIN is brute-forceable by anyone holding the phone. The comment in the code says exactly that rather than implying security it does not provide.
- **Verified the whole chain in a browser, and caught myself repeating a bug.** PIN unlock, board, "why ranked here" (Category +50, Not yet acknowledged +10, total 60), then Acknowledge dropping it to 50 live. The board also showed "1 reporters" — the identical plural defect fixed one phase earlier, reintroduced at a new call site because the helper existed but the string pair did not.

## Phase 4 — Uplink and responder dashboard (2026-09-26)

- **D-006 decided itself once the constraint was named.** The question looked like a preference between two hosted Postgres options. It was not: ADR-003 says no custom backend, so the phone uploads directly and the browser reads directly, which requires a client-callable API and row-level security that make a public key safe. Supabase ships both; Vercel Postgres hands you a connection string, which cannot go in a bundle and would have forced exactly the serverless layer ADR-003 rejects. The architecture had already made the choice a phase earlier.
- **The ADR-006 dividend finally paid out in full.** Phase 4 was originally "port the engine to TypeScript and build a second app". It became one route calling the same `compute()` over rows read back from Postgres. The dashboard cannot drift from a station board by construction, and there is a test asserting that the same observations produce byte-identical incidents on both sides of an upload.
- **The database enforces immutability, not the client.** BR-002 says observations never change, but an upsert is an UPDATE when the row exists, so anon needs an update path. Rather than trusting every client to send the same values, a trigger overwrites every column with the old value and increments `upload_count`. A malicious or buggy client can waste a request; it cannot rewrite what a barangay reported. `first_uploaded_at` is pinned the same way, because the dashboard diffs "since last sync" against it.
- **An acceptance criterion became a CI step.** "No admin or service key appears in the web bundle" is only worth anything if it is checked every time, so CI now greps `dist/` for `service_role` and fails the build. Checking it once by hand would have proved nothing about next week.
- **`uploaded` is a local-only flag, and that distinction is load-bearing.** Marking an observation uploaded looks like it violates BR-002 until you notice the field never leaves the device. It also matters for BR-008: own observations are protected from eviction only until they are uploaded, so failing to mark them would slowly fill a resident store with data it is not allowed to evict.
- **Dropped the Leaflet map deliberately, not accidentally.** It is item 2 on the plan's own cut list, it needs a web-only module and CSS that would not bundle for native, and a responder reads the ranked list. Writing down which cut was taken, and why, beats discovering the gap during the demo.

## Phase 5 — Field test kit and submission material (2026-09-26)

- **Wrote the field test as a run sheet, not a reminder.** Four documents already pointed at `docs/FIELD_TEST.md` and it did not exist. It is now a sheet someone who did not build the app can execute in one sitting: device roster, scripted observations with the expected grouping stated in advance so a wrong answer is obvious, blank tables for encounter durations and battery, and the diagnosis to reach for when three FLOOD reports stubbornly stay three incidents.
- **The most valuable line in it is a warning about ourselves.** Section 6 tells whoever tunes R or T that the eleven test vectors carry hand-computed expectations which assume the current values, so changing a constant means recomputing them by hand — and not the night before submission. The cost of writing vectors honestly is paid later, by someone who needs to know it is coming.
- **Planned for the test not happening.** D-011 has been open since the pivot, so the run sheet ends with what to do if no devices materialise: show `/sim`, and describe it as evidence about the protocol and not about radios. Deciding that now, in writing, beats improvising it on camera at midnight.
- **The submission doc exists because "working project" is the easy part.** A public repo still says the licence is undecided, which on a public repo means nobody may legally use what we built. That is the kind of item that is invisible until it is fatal, so it is a checkbox with a sentence explaining why it matters rather than a line in a list.
- **Drafted the honest-limits paragraph once and pointed three places at it.** README, video and Devpost should say the same thing about the cross-platform mesh, iOS foreground-only carrying and corroboration counting devices. Writing it three times is how three subtly different claims get made.

## Phase R0 — Wire hygiene (2026-09-27)

- **A comment is not a guarantee.** `types.ts` said the local-only fields were "never sent over the wire", and `encodeBatch` JSON-serialized whole observations anyway. The first leak test failed on the current code with all 17 fields in the payload, `own` and `uploaded` included. A receiving phone would have treated a relayed report as its own: protected from eviction (BR-008) and possibly marked uploaded when it never was.
- **Fixed once, in the shared function.** `toWire` runs inside `encodeBatch`, not at each call site, so `SyncSession` today and the QR path in R2 both get it without remembering to. A test keeps `WIRE_FIELDS` and `toServerRow`'s columns naming the same set, so the next new field can't slip into one and not the other.
- **Received data is untrusted input.** One observation with a non-UUID id would have made `encodeSummary` throw on every later encounter, which silently breaks a phone's sync forever. `isObservation` drops malformed items at the door instead of repairing them.
- **Receiving never overwrites.** When a peer echoes back an observation we created, the merge keeps our copy, so `own` stays true. One store entry point, `receiveObservations()`, is the only thing that writes received data, and the sync tests and `/sim` now run through the same `mergeReceived`.

## Phase R1 — Evidence and freshness (2026-09-27)

- **Fixtures first, again, and one cross-check we didn't write ourselves.** The three evidence fixtures were computed by hand from BR-011/BR-012 before `Evidence.ts` existed, including one second either side of each freshness boundary. A second test re-counts freshness over the 11 engine vectors and must match what the ARGUS analysis counted independently (10 fresh, 2 aging, 2 stale, with vector 06 exactly on the one-hour line). Two sources agreeing is worth more than one.
- **The timeline reuses the engine's rule instead of copying it.** Status matching was a one-line expression buried inside `statusOf`. Exporting it as `statusRefersTo` and calling it from both places means the timeline and the status badge can't disagree, and the 11 vectors prove the engine's behaviour didn't move.
- **One type error, 88 messages.** `tabularNums` was declared `as const`, which made its array readonly, and React Native's style type wants a mutable one. Every screen that spread it failed to typecheck. The fix was one line in `tokens.ts`, not 88 casts; the file that didn't use it having zero errors is what pointed at the cause.
- **Checked on screen, not just in tests.** At 390 px in the browser: the report button now names what's missing and scrolls to it, the PIN field border is visible, the hint uses the darker amber, the dashboard shows a designed notice instead of environment-variable names, and the board's scores add up by hand (74 = 30 + 20 + 14 + 10). The Filipino strings fit too, but they are still drafts for a native speaker.

## Phase R2 — QR bundle transfer (2026-09-27)

- **QR sits beside the transport, not behind it.** A QR exchange has no discovery and no two-way channel, so forcing it into `Transport` would have been a fake adapter (ADR-008). Instead `qr.ts` reuses the three pieces that matter: `encodeBatch` (so R0's `toWire` strips local-only fields for free), the existing urgency ordering, and R0's single `receiveObservations()` ingest path. The only new wire code is framing.
- **No Buffer, no platform.** React Native has no `Buffer`, and core may not touch the platform, so base64 is a small pure function, tested byte-for-byte against Node's encoder for every padding case. `fflate` does the deflate in plain JavaScript, so compression stays in core too.
- **The linter caught a render-time side effect.** Recording "which IDs did this page carry" inside `useMemo` wrote to a ref during render; `react-hooks/refs` rejected it. Moving it to an effect is correct in strict mode too, where a memo can run twice.
- **Our own tools misled us twice, and measuring caught both.** The browser window could not shrink below about 500 px, so the R1 "390 px" screenshots were really about 500 px. Re-checked with device emulation at a true 390 px: no clipping or horizontal scroll on any screen, and the QR card is exactly width − 32 px. And typecheck failed on `/share` and `/scan` because a gitignored, generated route-types file was stale; CI never sees that file.
- **Not proven yet: the camera.** Everything up to the screen is tested, but whether Expo Go on these iPhones catches frames fast enough is exactly what the RS spike measures. If it doesn't, the fallback is two constants in `rules.ts`.

## Phase R3 — Honest propagation status (2026-09-27)

- **Each step shows its own evidence, not a ladder.** The obvious design is a progress bar where "reached a station" implies "passed on". But a report can be uploaded straight from the phone that made it without ever being passed on, and ticking "passed to another phone" then would be a small lie. Each of the four steps shows only its own flag, and a test pins the uploaded-but-never-passed case.
- **Status moves only on evidence the phone holds.** A scanned QR receipt, or (for R6) a batch `SyncSession` actually sent; the new `onSent` callback reports the IDs and the role the peer claimed. The station role is trusted, not verified, and the QR screen says "It says it is a station" rather than asserting it.
- **Only the reporter's own copy moves.** A phone carrying someone else's report doesn't get a status for it, because that status belongs to the phone that made it. The flags are local-only like `uploaded`, so R0's `toWire` already keeps them off the wire; a test proves they reach neither a batch nor a server row.
- **The old success message was quietly overclaiming.** "Recorded. It passes on when you meet another phone" promised automatic sending that QR doesn't do. It's now just "Recorded.", followed by the status steps and the footer saying this is only what this phone knows.
- **A bug found by touching the screen.** My data confirmed deletes with `Alert.alert`, which React Native Web doesn't implement, so delete silently did nothing on the web build. It's now an inline confirm, checked working in the browser.

## Phase R4 — Known and not yet reported (2026-09-27)

- **"Nearby" is measured member to member, and a fixture proves why.** The plan's first draft compared incident centres. ARGUS found 3.5 % of benchmark incidents are wider than the 300 m radius, so one fixture builds a 434 m flood chain with a trapped report 278 m from its far end but about 495 m from its centre. Member to member finds it; centre to centre would have listed "Trapped: no report yet" for people who had been reported.
- **Wording is the feature.** An unknown is always a missing report ("Trapped: no report yet"), never an absence ("no one trapped"). The difference is the whole point of BR-013: silence in a disaster is missing information, not good news. Unknowns use the amber uncertainty colour, never red.
- **Resolved and old reports don't count as known.** A resolved medical case next door, or a shelter report from eight hours earlier, would make the picture look more complete than it is; both have a fixture.
- **Cost decides where it runs.** Gaps are computed only for the incident being viewed: on the detail screen, and on the dashboard only for the card you open. A whole board would be O(incidents²) on every change (110 ms on the benchmark).
- **Dropped an unused parameter.** The plan's signature took `now`, but nothing here depends on the current time, only on `lastSeen` values, so `gapsFor` doesn't take it.

## Phase R5 — Coverage per area (2026-09-27)

- **Silence has to be drawn, or it reads as safety.** A purok with no reports simply doesn't appear on a list of incidents, and an operator scanning the board can take its absence as good news. Coverage makes the gap visible: a purok the station expects to hear from and hasn't shows "No reports — this does not mean it is safe", sorted to the top, thinnest information first.
- **High coverage is blue, not green.** Many phones reporting from an area means someone is there, not that the area is fine. Green stays reserved for resolved incidents and explicit safe check-ins.
- **Every observation type counts, and each boundary is pinned.** Check-ins and flood reports alike show that people are present. The fixture puts one area exactly at the 3-hour stale line, one phone just outside the 3-hour device window, and one purok spelled "PUROK  1" that must count with "Purok 1".
- **What has no location has no area.** A station's acknowledge or resolve carries no place of its own, so it is skipped rather than guessed; attributing it to the referenced reports' area is possible later if the field test shows it matters.
- **The expected-puroks list stays on the station.** It is the station's own knowledge of its barangay, kept locally and never sent, so the dashboard shows coverage without the "no reports" rows.

## Design re-skin (2026-09-28)

- **Two design briefs can't both be the source of truth.** `docs/design/DESIGN_BRIEF.md` (blue accent, system-font-only, "field logbook") was already locked and implemented; a second, newer brief arrived as a downloaded package ("logbook + stamp", coral + ballpen, Doto numerals). Rather than merge them silently, the scope was narrowed with the team first: re-skin the *existing* routes and components in place, no new screens or navigation (no Home/Report split, no station tab bar), so two days before the hackathon deadline nothing load-bearing was put at risk.
- **The npm font package beats a hand-bundled TTF for the same reason.** `@expo-google-fonts/doto` ships the font bytes in the bundle just like a manual TTF would (no runtime fetch), but skips the manual "find OFL file, verify license, wire `expo-font`" steps — same offline guarantee, less to get wrong before a demo.
- **A component ported verbatim from an untested design package had a real bug.** `Svg accessibilityElementsHidden importantForAccessibility="no"` (copied from the package's `pictograms.tsx`, which its own README admitted was "typechecked against stubs, not yet run on a device") throws a React warning on the web build: react-native-svg's web target forwards unknown RN accessibility props straight to the DOM node instead of stripping them. Typecheck and lint were both clean; only a Playwright console-error check caught it. Fixed by dropping the props — an `<svg>` isn't in the accessibility tree by default on either platform, and every pictogram already sits next to a text label.
- **Green for "safe" was cut, not carried over.** The old brief reserved green for resolved incidents and explicit safe check-ins; the new one bans green on data outright (ISO 22324 collision), no carve-out. Safe-checkin counts and resolved stamps now render in plain ink instead.
- **`useRef(...).current` read during render trips `react-hooks/refs`** (same rule R2's `LEARNING.md` entry hit) — the `Stamp` component's `Animated.Value` construction had to move to `useState(() => new Animated.Value(...))` instead of the ref idiom the design package shipped.
